# Техническое задание на разработку системы «Управление товарными остатками»

**Версия документа:** 1.0  
**Статус:** готово к разработке  
**Язык интерфейса:** русский  
**Тип продукта:** многопользовательское веб-приложение  

## 1. Цель продукта

«Управление товарными остатками» помогает торговой компании управлять запасами электроники на основании выгрузки из 1С или Google Таблиц. Система должна:

- объединять остатки всех магазинов и складов на уровне компании;
- выполнять ABC-анализ по выручке, валовой прибыли и количеству продаж;
- выполнять XYZ-анализ устойчивости спроса;
- рассчитывать дни запаса, страховой запас, точку заказа и рекомендуемое количество;
- предупреждать о дефиците и приближении точки заказа;
- выявлять неликвидные и избыточные остатки;
- позволять пользователю вручную корректировать рекомендацию с обязательным комментарием;
- формировать, выгружать и отправлять отчёты;
- обеспечивать единые данные для закупщика, руководителя и финансового директора;
- хранить версии импортов и позволять восстановить предыдущую версию.

## 2. Границы первой версии

### 2.1. Входит в первую версию

- вход по логину и паролю;
- три взаимоисключающие бизнес-роли и отдельная техническая роль администратора;
- ручной импорт XLSX и CSV;
- импорт по ссылке на опубликованную Google Таблицу;
- вставка диапазона из буфера обмена;
- мастер сопоставления колонок и сохраняемые профили импорта;
- версии наборов данных и откат;
- ABC/XYZ-анализ;
- расчёт запасов и заказов;
- дашборд, таблицы, фильтры и карточка товара;
- ручная корректировка рекомендации;
- черновики заказов без обязательного согласования;
- Excel-отчёты и отправка отчёта по email;
- аудит значимых действий;
- управление глобальными параметрами анализа всеми тремя ролями;
- демонстрационный набор данных.

### 2.2. Не входит в первую версию

- автоматический обмен с 1С по API;
- закрытая Google Таблица с OAuth-доступом;
- автоматическая отправка заказа поставщику;
- учёт бюджета закупки;
- наличие товара у поставщика;
- минимальная сумма заказа поставщику;
- складские лимиты;
- прогноз сезонности;
- мобильное приложение;
- автономная работа без интернета;
- обязательная цепочка согласования заказа.

### 2.3. Расширение после первой версии

Архитектура должна позволять добавить процесс:

`Черновик → На согласовании у руководителя → На согласовании у финансового директора → Согласован → Отправлен поставщику → Получен`.

Для расширения должны быть предусмотрены таблица истории статусов заказа и события аудита, однако в интерфейсе первой версии доступны только статусы `Черновик`, `Сформирован` и `Архивный`.

## 3. Пользователи и права

Один пользователь имеет ровно одну роль. Совмещение ролей не поддерживается. Закупщик, руководитель и финансовый директор являются бизнес-ролями. Администратор — отдельная техническая роль: он управляет учётными записями, но по умолчанию не имеет доступа к ассортименту, продажам, остаткам, финансовым показателям и заказам.

| Возможность | Закупщик | Руководитель | Финансовый директор | Администратор |
|---|:---:|:---:|:---:|:---:|
| Просматривать бизнес-данные и отчёты | Да | Да | Да | Нет |
| Загружать и активировать данные | Да | Да | Да | Нет |
| Создавать и применять профили импорта | Да | Да | Да | Нет |
| Откатывать версию данных | Да | Да | Да | Нет |
| Менять параметры расчётов | Да | Да | Да | Нет |
| Запускать пересчёт | Да | Да | Да | Нет |
| Создавать черновик заказа | Да | Да | Да | Нет |
| Редактировать количество заказа | Да | Да | Да | Нет |
| Архивировать свой черновик | Да | Да | Да | Нет |
| Архивировать чужой черновик | Нет | Да | Да | Нет |
| Экспортировать и отправлять отчёты | Да | Да | Да | Нет |
| Просматривать бизнес-аудит | Нет | Да | Да | Нет |
| Просматривать технический аудит пользователей | Нет | Нет | Нет | Да |
| Создавать, блокировать и редактировать пользователей | Нет | Нет | Нет | Да |
| Инициировать сброс пароля | Нет | Нет | Нет | Да |

Различие ролей первой версии в основном состоит в стартовом экране и доступе к аудиту. Права согласования добавляются в следующем этапе без изменения модели пользователей.

### 3.2. Стартовые экраны

- **Закупщик:** список «Заказать сейчас», затем «Заказать в ближайшее время».
- **Руководитель:** сводка дефицита, запасов, неликвидов и матрица ABC/XYZ.
- **Финансовый директор:** стоимость рекомендованной закупки, стоимость запасов и неликвидов, ABC по валовой прибыли.
- **Администратор:** список пользователей, состояние учётных записей и технический аудит.

### 3.3. Создание пользователей

Первый администратор создаётся техническим оператором развёртывания через серверную CLI-команду. После этого администратор создаёт, редактирует, блокирует и разблокирует учётные записи через раздел «Пользователи», назначая ровно одну роль. Удаление пользователя физически запрещено: запись можно только деактивировать. Администратор не может назначить себе бизнес-роль без создания отдельной учётной записи. Сброс пароля выполняется одноразовой ссылкой email; если SMTP не настроен, администратор создаёт одноразовую временную ссылку, которая показывается только один раз и действует 30 минут.

## 4. Основные пользовательские сценарии

### UC-01. Вход

1. Пользователь открывает страницу входа.
2. Вводит email и пароль.
3. Система проверяет данные и активность учётной записи.
4. После успеха открывает стартовый экран роли.
5. После пяти неудачных попыток вход блокируется на 15 минут.

**Ошибки:** неверные данные показываются без уточнения, существует ли email; заблокированный пользователь не входит.

### UC-02. Импорт XLSX/CSV

1. Пользователь открывает «Импорт данных».
2. Загружает один файл `.xlsx`, `.xls` или `.csv` размером не более 50 МБ.
3. Система показывает листы Excel; пользователь выбирает один лист.
4. Система вычисляет сигнатуру структуры файла и ищет подходящий профиль импорта.
5. При однозначном совпадении система автоматически применяет профиль и показывает сопоставление для проверки. Если профиль не найден или структура изменилась, система автоматически ищет строку заголовков и предлагает сопоставление полей вручную.
6. Пользователь подтверждает либо исправляет сопоставление и указывает шаг периодов: день, неделя или месяц, дату окончания последнего периода и порядок колонок.
7. Пользователь может сохранить настройки как новый профиль либо обновить выбранный профиль.
8. Система валидирует данные и показывает предварительный отчёт.
9. При критических ошибках активация запрещена; предупреждения можно подтвердить.
10. После подтверждения создаётся новая версия данных и запускается расчёт.
11. Новая версия становится активной только после успешного полного расчёта.

Профиль никогда не применяется скрытно: перед запуском всегда показываются его название, дата изменения и итоговое сопоставление. Если обязательная колонка исчезла, тип данных изменился или появились неоднозначные совпадения, быстрый импорт блокируется и открывается мастер.

### UC-03. Импорт из Google Таблицы

1. Пользователь публикует нужный лист Google Таблицы как CSV либо предоставляет ссылку вида `docs.google.com/spreadsheets/...` с публичным доступом на чтение.
2. Вставляет ссылку в системе.
3. Сервер загружает CSV и далее выполняет UC-02 начиная с сопоставления полей.

Если таблица закрыта авторизацией, система объясняет, что первая версия принимает только опубликованные таблицы, и предлагает скачать XLSX.

### UC-04. Вставка из буфера

Пользователь копирует прямоугольный диапазон с заголовками из Excel или Google Таблиц, вставляет его в поле импорта и проходит те же сопоставление и проверку, что при файловом импорте.

### UC-05. Откат данных

1. Пользователь открывает историю импортов.
2. Видит автора, время, источник, имя файла, число строк, число товаров и статус.
3. Выбирает успешную предыдущую версию и нажимает «Восстановить».
4. Подтверждает действие.
5. Система создаёт новую версию-копию выбранной и делает её активной. История не удаляется.

### UC-06. Просмотр обзора

Пользователь видит показатели активной версии, применяет глобальные фильтры и переходит из каждой карточки к отфильтрованному списку товаров.

### UC-07. Анализ ABC/XYZ

Пользователь выбирает показатель ABC, период и шаг XYZ, изучает матрицу AX–CZ, нажимает сегмент и получает список входящих товаров.

### UC-08. Поиск и фильтрация

Пользователь ищет по номенклатуре, характеристике и их кодам, фильтрует по категории, поставщику, ABC, XYZ, статусу, наличию и диапазонам значений. Фильтры можно сбросить одной кнопкой.

### UC-09. Карточка товара

Пользователь выбирает товар и видит исходные данные, историю спроса, расчёты, объяснение формул, предупреждения и журнал ручных изменений.

### UC-10. Ручная корректировка заказа

1. Пользователь нажимает «Изменить количество».
2. Вводит целое неотрицательное количество и обязательную причину длиной 5–500 символов.
3. Система сохраняет исходную рекомендацию, новое значение, автора и время.
4. В таблицах показывается признак «Изменено вручную».
5. Пользователь может вернуть рассчитанное значение; это также записывается в аудит.

Ручное значение действует только для активной версии данных. После нового импорта рекомендация рассчитывается заново.

### UC-11. Формирование заказа

1. Пользователь открывает «К заказу».
2. Выбирает все или отдельные позиции с положительным итоговым количеством.
3. Создаёт черновик.
4. Система фиксирует снимок исходных и ручных количеств.
5. Пользователь редактирует строки, название и комментарий.
6. Нажимает «Сформировать»; документ становится неизменяемым.
7. Для исправления создаётся копия сформированного заказа.

Если поставщик отсутствует в выгрузке, все позиции находятся в одном общем документе. Если поле поставщика есть, пользователь может сформировать отдельные документы по поставщикам.

### UC-12. Экспорт

Пользователь выбирает тип отчёта, текущие фильтры либо полный набор и получает `.xlsx`. Имя файла содержит тип отчёта и дату формирования.

### UC-13. Отправка отчёта

1. Пользователь нажимает «Отправить отчёт».
2. Указывает одного или нескольких получателей, тему и сообщение.
3. Выбирает вид отчёта и применённые фильтры.
4. Система формирует XLSX, отправляет его вложением через SMTP и записывает результат.
5. Пользователь видит успешный результат либо понятную ошибку доставки.

### UC-14. Изменение настроек

1. Пользователь открывает настройки расчётов.
2. Меняет параметры и видит список затрагиваемых показателей.
3. Подтверждает изменение.
4. Система сохраняет новую версию настроек и пересчитывает активный набор.
5. До завершения отображаются предыдущие результаты с пометкой «Идёт пересчёт».
6. При ошибке остаются предыдущие результаты и настройки.

### UC-15. Управление профилями импорта

1. Пользователь открывает «Импорт данных → Профили».
2. Просматривает название, источник, сигнатуру колонок, автора, дату изменения и дату последнего использования.
3. Создаёт профиль из успешно проверенного сопоставления, переименовывает его, делает копию или архивирует.
4. При обновлении профиля система создаёт новую версию настроек профиля и сохраняет прежнюю в аудите.
5. Архивный профиль не подбирается автоматически, но остаётся связанным с ранее выполненными импортами.

Профиль хранит сопоставление полей, строку заголовков, лист по умолчанию, финансовый смысл неоднозначных колонок, правила определения периодов и порядок колонок. Конкретная дата последнего периода не сохраняется как постоянное значение: пользователь подтверждает её при каждом импорте, если дата не содержится в файле.

### UC-16. Управление пользователями

1. Администратор открывает раздел «Пользователи».
2. Создаёт пользователя с именем, email и одной ролью либо редактирует существующего.
3. Может заблокировать/разблокировать вход или инициировать сброс пароля.
4. Система не позволяет деактивировать последнего активного администратора и не позволяет назначить пользователю несколько ролей.
5. Каждое действие фиксируется в техническом аудите.

## 5. Структура входной таблицы

### 5.1. Поддерживаемая широкая форма

Одна строка соответствует одному товару. Колонки `1 … N` содержат количество продаж за последовательные периоды. Период `1` по умолчанию считается самым старым, `N` — самым новым. В мастере импорта пользователь может переключить порядок.

По предоставленному образцу распознаются поля:

| Заголовок образца | Внутреннее поле | Обязательность | Правило |
|---|---|---:|---|
| `Номенклатура` | `product_name` | Да | Непустая строка |
| `Характеристика номенклатуры` / `Характеристика` | `variant_name` | Нет | Размер, цвет, память, комплектация или другая модификация; пустое значение означает товар без характеристики |
| `Код характеристики` | `variant_code` | Нет | Стабильный идентификатор характеристики из 1С |
| `Объем продаж, шт` → `1 … N` | `sales_periods[]` | Да | Числа; пустая ячейка = 0 |
| `Объем продаж/Маржа (Наценка) за весь период, руб.` | `source_financial_total` | Нет | Тип показателя уточняется в мастере |
| `За сколько нам приходит товар от поставщика, дн` | `lead_time_days` | Нет | Целое ≥ 0, по умолчанию 5 |
| `На сколько по времени могут задержать поставки, дни` | `delay_days` | Нет | Целое ≥ 0, по умолчанию 0 |
| `Как часто мы заказываем товар, дни` | `review_period_days` | Нет | Целое ≥ 1, по умолчанию 7 |
| `Изменение спроса` | `source_demand_change` | Нет | Справочное; расчётное значение имеет приоритет |
| `Тек.остаток, шт` | `stock_qty` | Да | Число; отрицательное допустимо с предупреждением |
| `Тек.остаток, руб` | `stock_value` | Нет | Число ≥ 0 |
| `Всего продано, шт` | `source_total_sold` | Нет | Проверочное значение |
| `Средняя Себестоимость 1 единицы` | `avg_cost` | Нет | Число ≥ 0 |
| `Средняя Цена 1 единицы` | `avg_price` | Нет | Число ≥ 0 |
| `Кол-во месяцев продажи` | `months_with_sales` | Нет | Проверочное значение |

Дополнительно поддерживаются необязательные колонки: `Код 1С`, `Категория`, `Поставщик`, `В резерве`, `В пути`, `Магазин`, `Склад`, `Закупочная цена`. Если у одной номенклатуры есть характеристики, каждая комбинация номенклатуры и характеристики должна находиться в отдельной строке и анализироваться как самостоятельная товарная позиция.

### 5.2. Параметры периодов при импорте

Если в файле нет календарных дат, обязательны:

- гранулярность: `день`, `неделя` или `месяц`;
- дата окончания последнего периода;
- порядок: слева направо от старого к новому либо наоборот.

Система вычисляет границы остальных периодов назад. Для недели используется семидневный интервал, заканчивающийся датой последнего периода. Для месяца используются календарные месяцы. Для дня — календарные даты.

При выборе шага XYZ система агрегирует исходные периоды вверх. Дневные данные можно анализировать по дням, неделям или месяцам; недельные — по неделям или месяцам; месячные — только по месяцам. Дезагрегация запрещена.

### 5.3. Идентификация товара

Аналитической единицей является товарная позиция, то есть номенклатура с конкретной характеристикой. Ключ строится в следующем порядке:

1. `Код 1С + Код характеристики`, если доступны оба кода.
2. `Код 1С + нормализованное наименование характеристики`, если есть только код номенклатуры.
3. `Нормализованное наименование номенклатуры + нормализованное наименование характеристики`, если кодов нет.

Для товара без характеристики вторая часть ключа имеет специальное пустое значение. При нормализации удаляются крайние пробелы, повторные пробелы сворачиваются, сравнение выполняется без учёта регистра. Исходные написания сохраняются для отображения.

Две строки с одинаковым составным ключом являются критической ошибкой импорта. Автоматическое объединение дублей запрещено. Строки с одинаковой номенклатурой, но разными характеристиками не объединяются: для каждой отдельно рассчитываются спрос, ABC/XYZ, остаток, точка и количество заказа.

### 5.4. Финансовые показатели

Если доступны средняя цена, средняя себестоимость и количество:

- `Выручка = max(0, Всего продано) × Средняя цена`;
- `Себестоимость продаж = max(0, Всего продано) × Средняя себестоимость`;
- `Валовая прибыль = Выручка − Себестоимость продаж`.

Если есть отдельные готовые колонки выручки и валовой прибыли, они имеют приоритет. Для неоднозначной колонки `Объем продаж/Маржа` мастер требует выбрать одно значение: `Выручка`, `Валовая прибыль`, `Наценка` или `Не импортировать`.

Источник `Всего продано, шт` сравнивается с суммой периодов. Расхождение более `max(1 шт., 1%)` создаёт предупреждение. В расчётах спроса используется сумма периодов.

### 5.5. Возвраты

Продажи уже поступают за вычетом возвратов. Положительные нетто-значения используются как есть. Отрицательное значение периода сохраняется для контроля, но в расчёте спроса заменяется на 0 и вызывает предупреждение. ABC по количеству использует сумму `max(0, значение периода)`.

## 6. Валидация импорта

### 6.1. Критические ошибки

- отсутствует наименование;
- нет ни одной колонки периодов;
- дубли составных ключей товарной позиции;
- выбранная дата или гранулярность не определена;
- в обязательной числовой колонке текст, который невозможно преобразовать;
- файл пуст, повреждён или превышает 50 МБ;
- число строк превышает 50 000.

При критической ошибке набор не активируется.

### 6.2. Предупреждения

- отрицательный остаток;
- отрицательная нетто-продажа периода;
- расхождение итоговой продажи с суммой периодов;
- нет цены или себестоимости;
- история короче минимальной;
- отсутствует поставщик;
- отсутствуют срок или задержка поставки;
- выброс спроса;
- нулевая/отрицательная валовая прибыль;
- неизвестная дополнительная колонка.

Пользователь может скачать Excel с ошибками и предупреждениями.

## 7. Версионирование данных

- Импорт не изменяет активную версию до окончания проверки и расчёта.
- Каждая успешная загрузка создаёт неизменяемую версию.
- Активна ровно одна версия.
- Хранятся последние 10 успешных версий, но не менее 12 месяцев. Более старые удаляются фоновой задачей, если не связаны с заказом или аудитом.
- Неуспешные импорты хранятся 30 дней без исходного файла, только с протоколом ошибок.
- Откат создаёт новую версию, а не изменяет старую.
- Исходный файл хранится в защищённом файловом хранилище вместе с контрольной суммой SHA-256.

## 9. ABC-анализ

ABC рассчитывается параллельно по:

1. выручке;
2. валовой прибыли;
3. проданному количеству.

Для каждого показателя:

1. Товары с положительным значением сортируются по убыванию, затем по наименованию.
2. Рассчитываются доля и накопительная доля.
3. Товар получает A, если накопительная доля до добавления товара меньше границы A.
4. Получает B, если она меньше границы B.
5. Остальные получают C.
6. Нулевое или отрицательное значение получает C и признак `Нет положительного вклада`.

Таким образом товар, пересекающий порог, остаётся в более высоком классе. По умолчанию интерфейс показывает ABC по валовой прибыли. Доступен режим расчёта по всей компании и внутри выбранной категории; основной сохранённый класс рассчитывается по компании.

## 10. XYZ-анализ

Для каждого товара формируется ряд выбранного шага. Пустая ячейка и отсутствующий период считаются нулём.

- `Среднее = сумма спроса / число периодов`.
- Стандартное отклонение рассчитывается как генеральное (`STDEV.P`).
- `CV = стандартное отклонение / среднее × 100%`.

Классы:

- X: `CV ≤ 10%`;
- Y: `10% < CV ≤ 25%`;
- Z: `CV > 25%`.

Пороговые значения берутся из активной версии настроек. Если среднее равно 0, XYZ не назначается, состояние — `Нет спроса`. Если периодов меньше минимального значения, состояние — `Недостаточно данных`.

### 10.1. Выбросы

Выбросом считается значение выше `Q3 + 3 × IQR` при наличии не менее 8 периодов. Оно всегда отображается на графике. По умолчанию выброс участвует в расчёте. При включённой настройке исключения он заменяется медианой ряда только для прогноза, точки заказа и XYZ; исходное значение и ABC не изменяются.

### 10.2. Изменение спроса

Сравниваются средние значения последней и предпоследней третей доступного ряда:

`Изменение спроса, % = (Последнее среднее − Предыдущее среднее) / Предыдущее среднее × 100%`.

Если предыдущее среднее равно 0, а последнее больше 0, статус — `Возник спрос`; если оба равны 0 — `Без изменений`. Поле из выгрузки хранится как справочное, но не заменяет расчёт.

## 11. Расчёт заказа

Все промежуточные вычисления выполняются с полной точностью; отображение округляется до двух знаков, итог заказа — вверх до целой штуки.

### 11.1. Входные значения

- `Остаток = stock_qty`.
- `Резерв = reserve_qty`, при отсутствии 0.
- `В пути = in_transit_qty`, при отсутствии 0.
- `Свободный остаток = max(0, Остаток − Резерв)`.
- `Позиция запаса = Свободный остаток + max(0, В пути)`.
- `Эффективный срок поставки = Срок поставки + Возможная задержка`.
- `Средний спрос периода` — среднее ряда после выбранной обработки выбросов.
- `Длина периода`: день = 1, неделя = 7, месяц = 30,4375 дня.
- `Средний дневной спрос = Средний спрос периода / Длина периода`.
- `σднев = σпериода / √Длина периода`.

### 11.2. Формулы

- `Защитный период = Эффективный срок поставки + Интервал заказа`.
- `Страховой запас = z × σднев × √Защитный период`.
- `Точка заказа = Средний дневной спрос × Эффективный срок поставки + Страховой запас`.
- `Целевой запас = Средний дневной спрос × Защитный период + Страховой запас`.
- `Расчётная рекомендация = max(0, Целевой запас − Позиция запаса)`.
- `Рекомендуемый заказ = ceil(Расчётная рекомендация)`.
- `Дни запаса = Свободный остаток / Средний дневной спрос`.
- `Стоимость рекомендации = Итоговое количество × Средняя себестоимость`.

При нулевом среднем спросе заказ равен 0, дни запаса не вычисляются. Если истории недостаточно, система всё равно показывает ориентировочный заказ по доступным периодам, но помечает его низкой надёжностью.

`Итоговое количество` равно ручному значению, если оно установлено, иначе рассчитанной рекомендации.

## 12. Статусы товара

Товар может иметь один основной статус и несколько предупреждений. Основной статус определяется в указанном порядке:

1. **Нет в наличии:** свободный остаток `≤ 0`, средний спрос `> 0`.
2. **Риск неликвида:** остаток `> 0`, нет положительных продаж 90 и более календарных дней.
3. **Заказать сейчас:** средний спрос `> 0` и (`Позиция запаса ≤ Точка заказа` либо `Дни запаса ≤ Эффективный срок поставки`).
4. **Заказать в ближайшее время:** средний спрос `> 0` и `Дни запаса ≤ Эффективный срок поставки + 3 дня`.
5. **Избыточный запас:** средний спрос `> 0`, дни запаса больше 90.
6. **Снижение активности:** остаток `> 0`, нет положительных продаж 60 и более дней.
7. **Недостаточно данных:** периодов меньше минимального количества.
8. **Запас в норме:** остальные случаи.

Пороги берутся из настроек. Дополнительные предупреждения: отрицательный остаток, отрицательная прибыль, выброс спроса, отсутствующая цена, ручная корректировка, низкая надёжность.

Для широкого файла без точных дат последней продажи дата оценивается по последнему периоду с положительным спросом. Для месячных данных возраст спроса считается от конца соответствующего месяца, поэтому точность статуса неликвида ограничена месяцем.

## 15. Отчёты и экспорт

### 15.1. Виды отчётов

1. **К заказу** — все позиции с итоговым количеством больше 0.
2. **Заказ по поставщикам** — отдельный лист на каждого поставщика плюс сводный лист.
3. **ABC/XYZ** — классы, доли, CV и матрица.
4. **Неликвиды** — неликвиды, снижение активности и избыток.
5. **Все товары** — полный расчёт.
6. **Финансовая сводка** — стоимость запасов, рекомендаций и неликвидов.
7. **Протокол качества данных** — ошибки и предупреждения импорта.
8. **История заказов** — сформированные документы за выбранный период.

### 15.2. Формат XLSX

- каждая строка товарного отчёта содержит номенклатуру и характеристику в отдельных колонках;
- первая строка содержит название и дату;
- вторая — активную версию и параметры анализа;
- заголовки закреплены, включены автофильтры;
- денежные значения имеют формат RUB;
- количество — целое, показатели — до двух знаков;
- цвета статусов соответствуют интерфейсу;
- строки не содержат формул, результаты экспортируются значениями;
- максимальная длина имени листа соблюдается;
- экспорт не должен содержать пароль, токены или служебные идентификаторы.

### 15.3. Отправка email

SMTP задаётся переменными окружения. Получатели вводятся вручную и проверяются как email-адреса. Ограничение — 20 получателей и вложение до 20 МБ. Отправка выполняется в фоне, повтор при временной ошибке — до трёх раз. В аудит записываются отправитель, получатели, тип отчёта, время и результат, но не тело вложения.

## 16. Модель данных

Денежные значения хранятся как `numeric(18,2)`, количества и коэффициенты — `numeric(18,6)`, даты — UTC с отображением в часовом поясе организации.

## 17. API

API реализуется по REST под `/api/v1`. Минимальные группы:

- `/auth/login`, `/auth/logout`, `/auth/me`, `/auth/password-reset`;
- `/users`, `/users/{id}`, `/users/{id}/block`, `/users/{id}/unblock`, `/users/{id}/password-reset` — только администратор;
- `/imports`, `/imports/{id}`, `/imports/{id}/issues`, `/imports/{id}/activate`, `/imports/{id}/restore`;
- `/import-profiles`, `/import-profiles/{id}`, `/import-profiles/{id}/archive`, `/import-profiles/match`;
- `/versions`, `/versions/active`;
- `/products`, `/products/{id}`, `/products/{id}/adjustment`;
- `/analytics/summary`, `/analytics/abc-xyz`, `/analytics/obsolete`;
- `/settings`, `/settings/history`;
- `/orders`, `/orders/{id}`, `/orders/{id}/form`, `/orders/{id}/archive`;
- `/reports/export`, `/reports/send`;
- `/audit`.

Списки используют серверную пагинацию, фильтрацию и сортировку. Мутации принимают идемпотентный ключ. Ответы ошибок имеют единый формат: `code`, `message`, `fieldErrors`, `requestId`.

## 18. Архитектурные требования

ТЗ не фиксирует конкретные NPM-пакеты, UI-фреймворк, ORM, библиотеку графиков, XLSX или валидации. Исполнитель выбирает поддерживаемые библиотеки, подтверждает их лицензии и документирует ключевые решения в ADR. Выбор считается допустимым, если выполняются функциональные требования, показатели производительности, безопасности, тестируемости и развёртывания из этого документа.

Обязательные архитектурные свойства:

- отдельные клиентский интерфейс, серверный API и централизованное постоянное хранилище;
- реляционная база данных промышленного уровня; PostgreSQL является рекомендуемым вариантом;
- атомарные транзакции для активации версии данных и формирования заказа;
- серверные сессии в защищённых cookie либо эквивалентный механизм, не раскрывающий токены JavaScript-коду;
- фоновое выполнение долгих импортов, расчётов и email с защитой от дублирования;
- серверная валидация всех входных данных независимо от клиентской проверки;
- автоматизированные модульные, интеграционные и сквозные тесты;
- контейнерное развёртывание приложения и базы данных; Docker Compose является базовым поставляемым способом запуска;
- reverse proxy и TLS предоставляются средой размещения.

Приложение разворачивается либо в облаке, либо на сервере компании из одного комплекта артефактов. Секреты, SMTP и строка подключения задаются переменными окружения. Данные не должны зависеть от `localStorage`; в нём допустимо хранить только несекретные UI-предпочтения.

## 19. Конкурентная работа

- Активная версия данных переключается одной атомарной транзакцией.
- Пока импорт обрабатывается, пользователи продолжают видеть предыдущую активную версию.
- Ручное изменение использует optimistic locking по номеру версии записи. При конфликте пользователь получает свежие данные и повторяет изменение.
- Сформированный заказ является неизменяемым снимком и не меняется после нового импорта.
- Одновременный пересчёт одинаковой версии и настроек дедуплицируется.
- На всех экранах показывается идентификатор/время активной версии, чтобы исключить работу с незаметно устаревшими данными.

## 20. Безопасность

- только HTTPS в production;
- пароль минимум 10 символов;
- пароли хранятся только как результат современного адаптивного алгоритма хэширования с индивидуальной солью; конкретный алгоритм и параметры фиксируются в ADR и проходят проверку безопасности перед выпуском;
- cookie сессии недоступна JavaScript, передаётся только по HTTPS и имеет безопасную политику SameSite;
- CSRF-защита мутаций;
- защита от XSS, SQL-инъекций и загрузки исполняемых файлов;
- проверка MIME, расширения, размера и структуры импорта;
- ограничение частоты входа и тяжёлых операций;
- авторизация проверяется сервером на каждом запросе;
- журналы не содержат паролей, токенов и полного содержимого выгрузок;
- скачивание исходного файла доступно только авторизованным пользователям;
- аудит нельзя редактировать через приложение;
- сессия истекает после 8 часов бездействия, абсолютный срок — 24 часа;
- все секреты находятся только в переменных окружения.

## 21. Нефункциональные требования

Приняты оптимальные исходные значения:

- до 50 000 товаров/строк в одной широкой выгрузке;
- до 104 периодов на товар;
- до 20 одновременно работающих пользователей;
- импорт и полный расчёт 50 000 строк — не более 60 секунд на рекомендуемом сервере;
- открытие дашборда по готовым результатам — до 3 секунд на p95;
- фильтрация серверной таблицы — до 2 секунд на p95;
- экспорт 50 000 строк — до 60 секунд;
- интерфейс поддерживает desktop от 1280 px и планшет от 768 px;
- Chrome и Яндекс Браузер: две последние основные версии; Safari: две последние основные версии;
- доступность: клавиатурная навигация, видимый фокус, подписи полей, контраст не ниже WCAG AA;
- рабочий часовой пояс по умолчанию `Europe/Moscow`, настраиваемый при развёртывании;
- формат дат `ДД.ММ.ГГГГ`, валюта RUB, десятичный разделитель запятая;
- серверное логирование с `requestId`, мониторинг ошибок и health-check;
- ежедневная резервная копия PostgreSQL, хранение 30 дней;
- ежемесячная проверка восстановления резервной копии;
- расчёты детерминированы: одинаковые данные и настройки дают одинаковый результат.

## 22. Аудит

Неизменяемый журнал хранит:

- входы и блокировки входа;
- импорт, активацию и откат;
- создание, изменение, применение и архивирование профиля импорта;
- изменение настроек;
- ручное изменение заказа;
- создание, формирование и архивирование заказа;
- экспорт и отправку отчёта;
- техническое создание, блокировку и сброс доступа пользователя.

Аудит хранится минимум 3 года. Руководитель и финансовый директор могут фильтровать его по пользователю, действию, сущности и периоду, но не изменять.

## 23. Обработка ошибок

- пользователь всегда получает понятное русское сообщение и идентификатор ошибки;
- техническая трассировка показывается только в серверном журнале;
- неуспешный импорт не меняет активные данные;
- неуспешный пересчёт не меняет активные настройки и результаты;
- при сбое email отчёт остаётся доступен для скачивания;
- при потере соединения несохранённая форма сохраняется в памяти вкладки и повторная отправка не создаёт дубль;
- пустые состояния содержат следующее доступное действие: загрузить данные, снять фильтры или открыть демоданные.

## 24. Демонстрационные данные

В систему включается отдельный демонабор минимум из 60 товаров, покрывающий:

- все девять сегментов AX–CZ;
- отсутствие продаж;
- короткую историю;
- отрицательный остаток;
- отрицательную прибыль;
- выброс спроса;
- дефицит, раннее предупреждение, норму, избыток и неликвид;
- отсутствующие цену, поставщика и срок поставки;
- товар с ручной корректировкой;
- одна номенклатура с двумя характеристиками, имеющими разные спрос и остатки.

Демоверсия создаётся как обычная версия с явной меткой и может быть заменена импортом.

## 25. Тестирование

### 25.1. Модульные тесты

Обязательны тесты:

- границ ABC 80% и 95%;
- нулевых/отрицательных значений ABC;
- CV и границ X/Y/Z;
- нулевого спроса и короткой истории;
- всех формул заказа;
- срока с задержкой;
- пустых и отрицательных продаж;
- выбросов с включённым/выключенным исключением;
- приоритета статусов;
- нормализации наименований;
- формирования составного ключа номенклатуры и характеристики;
- сопоставления нумерованных колонок периодов;
- сигнатуры структуры файла и подбора профиля импорта;
- округления денег и количества.

### 25.2. Интеграционные тесты

- успешный и ошибочный импорт каждого формата;
- создание, автоматический подбор, обновление и архивирование профиля импорта;
- блокировка быстрого импорта при несовместимом профиле;
- атомарная активация версии;

- пересчёт после настройки;
- конфликт ручной корректировки;
- формирование неизменяемого заказа;
- XLSX-экспорт;

- разграничение прав;
- создание, блокировка и сброс доступа пользователя администратором;
- очистка старых версий.

### 25.3. Сквозные тесты

Для каждой бизнес-роли: вход, стартовый экран, импорт демоданных, поиск товара, просмотр карточки, ручная корректировка, создание заказа и экспорт. Для руководителя и финансового директора дополнительно — просмотр бизнес-аудита. Для администратора: вход, создание пользователя, смена роли, блокировка, разблокировка, сброс пароля и просмотр технического аудита; бизнес-разделы должны быть недоступны.

## 26. Критерии приёмки

Продукт принимается, когда:

1. Три бизнес-роли и администратор входят и получают права согласно матрице; администратор не видит бизнес-данные.
2. Образец широкой выгрузки с колонками `1 … N` импортируется через мастер; номенклатура с разными характеристиками остаётся разными аналитическими позициями.
3. XLSX, CSV, публичная Google Таблица и вставка диапазона работают; сохранённый профиль автоматически подбирается для повторной совместимой выгрузки и исключает повторное ручное сопоставление после подтверждения пользователя.
4. Ошибочный импорт не заменяет активные данные.
5. Новая версия полностью заменяет активный набор, а предыдущая восстанавливается через откат.
6. ABC по трём показателям совпадает с контрольными расчётами.
7. XYZ корректно работает для дня, недели и месяца в разрешённых сочетаниях.
8. Нулевые периоды участвуют в XYZ.
9. Срок, задержка и интервал заказа участвуют в формулах согласно разделу 11.
10. Все восемь основных статусов воспроизводятся на демоданных.
11. Ручная корректировка требует причину и видна в аудите.
12. Сформированный заказ не изменяется после новой загрузки.
13. Все заявленные фильтры, поиск и переходы с дашборда работают; интерфейс соответствует утверждённому прототипу и объективным требованиям раздела 13.1.
14. Карточка товара показывает график и расшифрованную формулу.
15. Каждый отчёт создаёт корректный XLSX.
16. Отчёт отправляется указанным адресатам при настроенном SMTP.
17. 50 000 строк обрабатываются в пределах заданных показателей.
18. Критические действия, управление пользователями и профилями импорта записываются в неизменяемый аудит.
19. Автоматические тесты проходят в CI.
20. Развёртывание выполняется документированной командой Docker Compose, миграции применяются автоматически контролируемым шагом.
